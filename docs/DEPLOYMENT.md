# Ledger Deployment Runbook

Ledger is not production-ready until this runbook has been applied to a real host and verified behind TLS.
The templates here provide process supervision and health checks; they do not replace live Sui/Walrus proof,
managed secrets, or provider-level replay support.

## Runtime Layout

Recommended host paths:

- App directory: `/opt/ledger`
- Environment file: `/etc/ledger/ledger.env`
- SQLite state: `/var/lib/ledger/ledger.db`
- Logs: systemd journal or a central log collector

Production env must set:

```bash
LEDGER_DB_PATH=/var/lib/ledger/ledger.db
LEDGER_MOCK=false
LEDGER_USE_V2_MINT=true
LEDGER_ENABLE_PAYMENTS=false
LEDGER_VERIFY_AUTH_TOKEN=<strong-token>
LEDGER_VERIFY_RATE_LIMIT_MAX=60
LEDGER_VERIFY_RATE_LIMIT_WINDOW_MS=60000
LEDGER_ALERT_WEBHOOK_URL=<ops-alert-webhook>
LEDGER_DATA_KEY_ID=<active-key-id>
LEDGER_DATA_ENCRYPTION_KEY=<managed-secret-value>
```

Keep `SUI_PRIVATE_KEY`, `LEDGER_DATA_ENCRYPTION_KEY`, alert tokens, Photon credentials, and provider tokens in
a managed secret store. If `/etc/ledger/ledger.env` is used, it must be generated by the secret manager at
deploy time and readable only by the `ledger` user.

## Preflight

Run these before enabling services:

```bash
npm ci
npm run build
npm run health
npm run test:config
npm run test:encryption
npm run test:create-record
npm run test:provider-offsets
```

`npm run health` validates required runtime config and SQLite initialization. It intentionally does not spend
gas or write to Walrus.

## systemd Services

Templates live in:

- `deploy/systemd/ledger-worker.service`
- `deploy/systemd/ledger-verify.service`

Install:

```bash
sudo install -d -o ledger -g ledger /opt/ledger /var/lib/ledger
sudo install -d -m 0750 /etc/ledger
sudo cp deploy/systemd/ledger-worker.service /etc/systemd/system/
sudo cp deploy/systemd/ledger-verify.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable ledger-worker ledger-verify
sudo systemctl start ledger-worker ledger-verify
```

Check:

```bash
systemctl status ledger-worker ledger-verify
journalctl -u ledger-worker -u ledger-verify -f
```

Both services run `npm run health` as `ExecStartPre`. If health fails, systemd will not start the process.

## TLS Boundary

`ledger-verify` listens on `LEDGER_VERIFY_PORT` and must sit behind a TLS reverse proxy. The proxy should:

- terminate TLS
- enforce request body/header limits
- forward only `/verify/:objectId`
- preserve `X-Forwarded-For` for rate limiting
- not expose any decrypt-capable route

The verify route intentionally returns anchors, hashes, and metadata only. Decrypt-capable commands remain
local/operator-only until delegated access is designed.

## Operational Checks

After deployment:

```bash
curl -fsS https://<host>/verify/<known_object_id>
npm run health
journalctl -u ledger-worker --since "15 minutes ago"
journalctl -u ledger-verify --since "15 minutes ago"
```

Confirm:

- services restart after process exit
- `LEDGER_ALERT_WEBHOOK_URL` receives error-level alerts
- `/verify/:objectId` returns `ok: true` for a known live object
- SQLite writes to `/var/lib/ledger/ledger.db`
- no logs contain private keys, raw financial messages, decrypted payloads, or data-key material

## Remaining Deployment Gaps

This runbook still needs live execution evidence before the process-supervision blocker can be closed. The
verify server also still needs a deployed TLS proof. Provider-level replay/resume remains limited by the
current Spectrum terminal/iMessage event shape, which does not expose a separate cursor.
